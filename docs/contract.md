# Outcome contract

Use the existing canonical record, identified by its owner and stable reference. Keep the original human request, later steering, current approval, selected outcome, acceptance IDs, accountable execution owner, register writer, owned paths, current subject, next action and finite stop conditions together. Separate employee role, account, chat title, author, reviewer and record writer.

An approval has a subject and scope. Keep the current authorized actions and current denials explicit; an old plan, a PDF, an installed plugin or an unrelated approval cannot enlarge them. Reversible work already authorized continues without repeated permission. Preserve spending, external sends, publication, merge, release, security, production and explicit stop gates. Included subscription access is neither zero usage nor unlimited usage. Read actual configuration when relevant; an unavailable usage display alone does not establish a capacity failure.

Acceptance IDs describe observable results with evidence, not arbitrary stages or elapsed time. Decompose a large requested product into useful slices while retaining deferred criteria in the original register. A slice completion cannot close the complete product. No new request or issue is fabricated from each derived test, prompt or theorem.

Each record must name an outcome stop, a concrete dependency stop and a waiting/resumption trigger when applicable. A one-off task ends at its delivered accepted outcome. A standing employee takes bounded authorized goals and waits when no authorized action remains. Do not add a schedule or perpetual loop to implement a one-time request.

The register writer incorporates accepted deltas. Helpers return artifact paths and hashes to that writer; they do not create competing canonical ledgers. Missing history stays an accounting gap. A blocker states the exact affected action, observation/error, responsible owner and next executable step. Continue independent authorized work around it.

Use [the approved completion contract](completion-contract.md) to retain original obligations and separate multipart and supporting outcomes. Restore native-goal bindings when selected; completion of a supporting record never closes its parent.
