# Coordinator and worker contracts

The existing coordinator resolves dependencies, maintains the next finite unit and accepts integration. A worker owns its branch and explicitly leased paths. A helper uses disjoint output paths. A reviewer has not authored the subject and writes a separate verdict. The register writer alone updates canonical accounting. On a small task, the same execution owner may integrate its own work but cannot become its own independent reviewer.

Before delegating, check the existing owner, task roster and local/PR artifacts in the named scope. Bounded negative searches do not establish global nonexistence. Preserve capable active owners; read status without interrupting them. Reuse current state and carry the original request, all steering, selected pstack adapter/playbook, permissions and acceptance into every resume. Use fresh non-author context for a required independent review.

Use [the brief template](../templates/worker-brief.md). Unknown verification commands become a bounded discovery step. Check dependencies and write-path overlap before admitting parallel helpers. Reserve time for integration, checks and delivery rather than filling every slot with new work. Select supported models from the current tool schema, honor an explicit user-selected model/effort and report unverified settings instead of guessing them. Different role names on one model are not cross-family review.

## Supported Cloud Tasks

Discover the supported task create/read/status tools on the current executor. Resolve project, execution environment, model availability, scope and existing spending authority before dispatch. Prefer an already working authorized cloud environment when it fits; a local-only request stays local. Do not substitute the Mac for a requested cloud VM without reporting that mismatch. Do not invent a Cloud Tasks CLI or provider grant.

Record these stages separately: requested, admitted with task identity, acknowledged, first verified action, artifact produced, worker ended, delivered, independently accepted. Creation success is admission only. Save the first successful read/tool result from the actual execution environment, then a concrete artifact/test checkpoint. A task's active label is not a process receipt. A saved goal or queued message is not execution.

If create returns cancellation or an unknown error, retain operation/request ID and timestamp. Check the supported roster and relevant artifacts for that attempt before any retry. No child ID means unconfirmed creation, not proven absence. A stale or truncated reader can omit tool activity; concrete artifact receipts may establish progress. Correlate the original failure rather than assigning an unrelated pipe or OS error as its cause. Do not replace an active writer to obtain a cleaner status display.

Configured connectors, child process access, actual backend binding and account scope are different facts. Read existing runtime configuration safely before proposing setup. Qualify child access when required with harmless checks; do not repeat paid inference just to check persistence. Stop at real access/authority limits and continue independent local work.

Native-goal assignments use [the lifecycle contract](completion-contract.md). Read the current goal, retain compatible work, and bind any authorized creation or completion to actual readbacks. Unsupported capabilities and conflicting objectives remain explicit dependencies.
