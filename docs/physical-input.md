# Verify physical input and capture

Use the current device or session owner for a requested mapping, dictation or peripheral change. Choose a harmless owned target for input. Do not exercise a shortcut in a messaging or destructive control merely because the key event is observable.

## Bind the intended behavior

Record the device and active profile, onboard or firmware mapping, operating-system mapping, application binding, focused target and expected press, hold and release behavior. Distinguish a hardware layer key from a modifier exposed to the operating system.

Preserve the working bindings, other profiles and a usable rollback. When an executable registers the shortcut, identify the actual executable and its lifetime. A saved configuration or permission screen does not prove a live registration.

## Exercise the physical control

1. Make the smallest authorized change in its owning layer. Preserve existing security controls and permission scope.
2. Test the real physical press, hold, release and repetition against the literal expected output. Check focus changes and modifier state where relevant.
3. Disconnect and reconnect the device or restart the owned application when that case is authorized. Verify actual profile and binding adoption.
4. Check rollback to the preserved mapping. Retain an untested rollback as an open case rather than claiming it works from a backup file alone.

For dictation, confirm the selected microphone, real input, insertion target and release behavior. A generated text fixture does not establish captured speech. If the available tools cannot hear or inspect the physical result, retain the recording privately and obtain the user's observation where needed.

For requested audio or video capture, use a bounded sample. Inspect or play the actual output and report which streams and intervals were observed. Keep recording, encoding, playback and authorized broadcast delivery separate. Stopping a browser runtime or closing a tab does not establish physical microphone or camera release. Verify release through supported device or operating-system evidence without disrupting another recording.

## Return evidence and acceptance

Return the layer map, preserved configuration, exact physical actions, expected and observed output, runtime identity, media coverage and rollback result. Use [verification](verification.md) for independent acceptance where required.

| Case | Required result |
|---|---|
| Normal | A declared push-to-talk control starts on press, remains active while held and stops on release. Its reconnect and rollback cases meet the declared mapping. |
| Reject | A stuck modifier, continued capture after release or input sent to the wrong focused application fails the corresponding criterion. |
| Incomplete | Settings appear correct but no physical input or actual audio was observed. Report configuration only and retain the physical acceptance dependency. |

These exercises do not grant device permissions, enable broadcasting or interrupt unrelated sessions.
